ARMv7 throughput on tib — the measurement §9.4 predicted
========================================================

2026-09-16. Host: tib (Tinker Board S, RK3288, Cortex-A17, armv7l, 4 cores, 2 GB).
Kernel: 7.2.6 #1 SMP PREEMPT_RT (mainline build). Governor `performance`,
`scaling_max_freq` 1416 MHz (rtpi's cap: this board cannot hold its top bin and the
15-minute suite once drove it to the 90 C critical trip). Temperature 46-52 C throughout,
never near a trip.

Tool: namchain-bench, 48 kHz, `double` samples, `a2_fast` ON, 2 s x 10 iterations per point.
Raw output: tib-bench-armv7-raw.txt (shipped build), tib-bench-armv7-neon-raw.txt (NEON).
Cross-built at commit 82356e3 on piv; armv7 unit tests 132/132 under qemu for the shipped
build and 133/133 for the NEON build (the extra case is the planar parity test).


THE HEADLINE
------------
**Tib runs one A2-Full per core with the planar kernels, and none without them.** RTF here is
CPU-seconds per audio-second, so RTF < 1 is faster than real time:

  shipped (-mfpu=vfpv3-d16)   RTF 1.3251, p50 block 1764.9 us  -> **cannot run A2-Full at all.**
                              One instance needs 133% of a core, and its *median* block already
                              exceeds the 1333.3 us deadline.
  NEON (-mfpu=neon-vfpv4)     RTF 0.5199, p50 690.1 us, p99 733.5 us -> **one instance per core,
                              genuine real time**, with 2 x 690.1 = 1380 us showing a second
                              would not fit even at the median.

Criterion 3's ">= 4 concurrent A2-Full at q64" is therefore unreachable on ARMv7, and the
binding reason is not the deadline but the threading model: **the engine renders single-threaded
on one pinned core, so four instances need 4 x 0.52 = 2.1 cores of CPU throughput.** The p99 gate
compounds it (4 x 55% = 220% of the deadline), but four instances would not fit on one core even
if every block met the deadline. On piv the same model is RTF 0.0501, so four cost 0.2 of a core
and fit comfortably -- which is what the clause encodes: a statement about an A76-class CPU, not
about the engine.

Two footnotes. The single instance NEON does fit sits at 55% of the deadline: *under* the
deadline, *above* criterion 3's 50% p99 gate, so even one A2-Full is marginal on this board. And
the plan's one-line prediction ("A2-Full counts will be much lower there") was directionally
right but understated the shipped build, which manages zero rather than few.

A2-Lite is the ARMv7 path, and the shipped build is leaving most of the CPU unused.


THE TWO BUILDS
--------------
The shipped armv7 configuration is `-march=armv7-a -mfpu=vfpv3-d16 -mfloat-abi=hard`
(cmake/toolchains/armv7-linux-gnueabihf.cmake). **vfpv3-d16 has no NEON**, so the compiler
emits no vector code at all on a CPU that has a NEON unit, and `a2_planar.h`'s ARMv7 arm
(`__arm__ && __ARM_NEON && __ARM_FEATURE_FMA`) does not fire -- the model is the portable
`A2FastModel<8>`. Measured instruction mix: **1 256** NEON-family instructions in the shipped
binary against **10 614** in the `-mfpu=neon-vfpv4` one (same source, same commit).

With `-mfpu=neon-vfpv4` both macros fire, the kernels select, and the model becomes
`A2PlanarFull` / `A2PlanarNano`.

Speedup from enabling NEON, at q64: **A2-Full 2.55x, A2-Lite 1.48x**. The A2-Lite figure
lands squarely on the 1.42-1.55x that section 9.4 predicted for PR #313's ARMv7 arm, which is
a useful confirmation that the prediction was sound. A2-Full gains more because 8 channels
map onto NEON vectors twice as well as 3 do.

Instances that fit, from %dl (a value v means one instance costs v% of the deadline, so
floor(50/v) fit the 50% gate and floor(100/v) fit 100%):

  model / build              at 50% of the q64 deadline     at 100%
  A2-Full shipped            0  (one instance is 136%)      0
  A2-Full NEON               0  (one instance is  55%)      1
  A2-Lite shipped            3                              8
  A2-Lite NEON               5                             11

For scale, the same engine on piv's A76 with the planar kernels: A2-Full q64 RTF 0.0501 and
A2-Lite 0.0087. So tib with NEON enabled is **~10x slower per model than piv**, and the
shipped ARMv7 build is **26x slower on A2-Full**.


WHAT THIS MEANS FOR THE PROJECT
-------------------------------
1. **Section 9.4's prediction is confirmed and sharpened.** ARMv7 should "prefer A2-Lite and
   aggressive slimming" -- measured, it must: A2-Full cannot run in real time at all.
2. **The shipped ARMv7 default leaves 1.5-2.5x on the table** by not enabling NEON on a CPU
   that has it. Section 9.4 already called this "a packaging decision for M6"; this measures
   what the decision is worth. The reason for the `vfpv3-d16` default is real -- it is the
   Debian armhf *ABI* baseline, so one binary runs everywhere armhf does -- but the artifact
   for a known-NEON board is a different build, not a runtime dispatch, because the kernels'
   selection is a compile-time macro.
3. **A reporting inconsistency worth fixing.** `NAMCHAIN_A2_PLANAR_ACTIVE` in CMakeLists.txt
   is gated on `CMAKE_SYSTEM_PROCESSOR MATCHES "^(aarch64|arm64|armv8)"`, but the kernels'
   own guard (`NAM_A2_PLANAR` in a2_planar.h) also fires for `__arm__ && __ARM_NEON &&
   __ARM_FEATURE_FMA`. So an armv7 NEON build reports "A2 planar NEON: OFF" at configure time
   while actually running the planar kernels. The parity test is compiled from `NAM_A2_PLANAR`
   rather than the CMake variable, so it is not silently skipped -- but the configure-time
   summary is wrong, and a CI job reading it would conclude the opposite of the truth.
4. **The throughput ceiling is CPU-shaped here, unlike piv.** piv was memory-bound before it
   was CPU-bound; on tib the first constraint is simply that the CPU is ~10x slower per model.
   The load-arm comparison in the plan is worth running for that reason: the *shape* of the
   loss should differ from piv's, and if it does not, that is informative too.


CORRECTNESS OF THE ARMv7 FAST PATH
----------------------------------
Enabling NEON also enables the planar kernels, whose bit-identity is the whole of their
claim. The parity test is guarded by `NAM_A2_PLANAR`, so it does not exist in the shipped
build (132 cases) and does exist in the NEON build (133 cases) -- it is not skipped.

  qemu-arm-static, piv:      133 cases / 230 854 assertions, 0 failed
  natively on tib:           133 cases / 230 854 assertions, 0 failed

The native run matters more than the emulated one, and it is the one that counts here: section
9.4 says ARMv7 bit-identity "rests on FPSCR.FZ being set (AArch32 NEON is unconditionally
flush-to-zero, scalar VFP is not)", and an emulator is not required to model that distinction
the way the silicon does. Both passed, so the ARMv7 planar fast path is verified bit-identical
on the hardware it would ship to -- evidence in tib-armv7-native-tests.txt.

Getting that run to be meaningful took two rounds, and the reason is worth recording: the
first native run reported 13 failures and the second 5, and *every one of them* was a fixture
missing from a path baked in at compile time (the vendored `example_audio/input.wav` and
`example_models/*.nam`), not a numerical difference. A test suite moved to another machine
without its fixtures fails in a way that looks exactly like a regression, so the fixture
deployment is part of the harness rather than an afterthought.


B2 — the engine loop on tib, no device
--------------------------------------
`namchain-soak --backend null`, 3 x A2-Lite, q64, 300 s, `--cpu 3`, SCHED_FIFO 80, NEON build,
RT kernel with no isolation (tib has none, and EXPECT_NO_ISOLATION records that as the
expected state rather than a failure). Evidence: tib-b2-null.*.

  block    p50 351 462 ns   p99 395 796 ns (29.68% of deadline)   max 627 966 ns
  chain    p99 392 004 ns (29.40%)
  deadline overruns 0      allocations 0      oracle max|diff| 0 over 60 s      PASS

This is the arithmetic from B1 holding up in the loop: three A2-Lite at 9.56% of the deadline
each predicts 28.7% p99, and the loop measures 29.68% with a maximum at 47% of the deadline.
So the engine's own cadence, timers, gates and oracle are sound on an in-order ARMv7 with no
core isolation -- what is left to test there is the device, and that is D1/§2.
