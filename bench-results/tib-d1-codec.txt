D1 — the first device arm on tib: the on-board codec cannot be opened full-duplex
================================================================================

2026-09-16, commit 82356e3 + the diagnostic change below. Host tib, kernel 7.2.6 PREEMPT_RT,
governor performance at 1416 MHz, 48.6 C. Build: `-mfpu=neon-vfpv4` (bin-neon), 3 x A2-Lite,
q64, `--device hw:1,0 --capture-channels 2 --playback-channels 2`.

RESULT: the engine refuses the device, correctly, with exit 2 before a single block runs.

  error: cannot open /dev/snd/pcmC1D0p: Invalid argument (the capture side opened, so the
  path is valid: this device appears not to support full-duplex capture+playback on the same
  PCM -- either direction alone works. Use a device that exposes the two directions
  separately, or a USB interface, which does)

WHY, MEASURED RATHER THAN GUESSED
---------------------------------
The on-board `rockchip,tinker-codec` (card 1) advertises both directions on device 0 and each
one works on its own:

  aplay   -D hw:1,0 -f S32_LE -r 48000 -c 2 -d 1 /dev/zero   -> plays
  arecord -D hw:1,0 -f S32_LE -r 48000 -c 2 -d 1 /dev/null   -> records
  aplay -l / arecord -l                                      -> both "device 0"

But they cannot be held open together, by anyone:

  open(pcmC1D0c, O_RDWR|O_NONBLOCK)                    -> ok
  open(pcmC1D0p, O_RDWR|O_NONBLOCK)                    -> EINVAL (22)
  the same with a 1.5 s delay between the two opens    -> EINVAL (still; not a race)
  open(pcmC1D0p) then open(pcmC1D0c)                   -> EINVAL on the second
  open(pcmC1D0p) twice                                 -> EBUSY (16), a different error

So `EINVAL` on the second direction is a specific, distinguishable answer -- "this PCM will not
be opened full-duplex" -- and not a bad path (`ENOENT`), a busy device (`EBUSY`), or a
malformed argument. The driver is `snd_soc_simple_card` with the RK3288 I2S; the reason is in
the driver, but the observable is what a backend has to act on.

WHAT THIS MEANS
---------------
1. **`alsa_raw` cannot use tib's on-board codec at all.** It opens both directions before
   configuring either, deliberately: the SSL's capture side is ASYNC with no explicit feedback
   endpoint and the driver wants the playback stream present (plan section 9.5). That design
   is not negotiable per-device, and a device that exposes one direction at a time is outside
   what this backend supports.
2. **This is the backend-generality finding the plan went looking for.** Every device
   `alsa_raw` has been measured on so far (PCM2902, Joyo MOMIX, SSL 2+ Mk II) is USB and
   full-duplex on one PCM. The first non-USB device it met is not, and the failure is clean:
   it refuses at open, before touching a block, rather than half-working.
3. **The device arms on tib need the SSL 2+**, which is being attached. `snd-aloop` and
   `snd-dummy` load on tib and remain the no-hardware fallback for loop-shaped tests, but they
   do not substitute for a real duplex device.
4. **The diagnostic was too thin, and is now fixed** (src/io/alsa_raw.cpp). "cannot open
   ...: Invalid argument" is accurate and useless: it sends the reader to the channel count
   and the sample rate, which are both correct and both accepted by `aplay`. The message now
   says that the capture side opened, so the path is valid, and that the device appears not to
   support full-duplex -- which is the actual finding, and is what a user hitting this on an
   SoC board needs to be told. `ctest` 4/4 after the change, and the message verified on tib.

This is also a small lesson about arm ordering, which the plan got right: B1 (throughput) and
this arm both needed no SSL, and both produced results worth having. Had the plan opened with
a device soak, this session would have produced nothing at all.
